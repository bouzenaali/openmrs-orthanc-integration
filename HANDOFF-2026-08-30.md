### 2.4 Error page crash on "green" theme — ⚠️ PARTIALLY FIXED 2026-09-07, root cause not captured

**What was seen:** `http://10.0.211.249:8080/openmrs/` returned a real HTTP 500 in a browser
session (French→English language switch, done earlier the same day). The page shown was
not OpenMRS's own error page but Tomcat's generic fallback, reporting:

```
javax.servlet.jsp.JspTagException: Theme 'green': No message found under code 'favicon' for locale 'en_US'.
```

**Root cause of the crash itself (confirmed, not guessed):** OpenMRS's own error page
(`WEB-INF/view/uncaughtException.jsp`) tries to render a `<spring:theme code="favicon"/>`
tag using whatever theme is active. The `chublidatheme` module forces theme `green`
(`ThemeInjectionFilter`) for every request. `green`'s resource bundle — bundled inside the
stock `legacyui-1.8.4.omod`, **not custom to this project** — only defines 3 keys
(`image.logo.bar`, `stylesheet`, `jqueryui.theme.name`) and does not inherit `favicon` from
`defaults.properties` the way OpenMRS's own themes do. So whenever *any* unrelated
exception occurs, the page built to display it throws a second exception, and the real
error is never shown to the browser and — separately — was not in any log file either,
because the JVM's `MEMORY_APPENDER` (the Log4j appender OpenMRS uses to capture error
detail) is not started: `ERROR Attempted to append to non-started appender MEMORY_APPENDER`
recurs in `docker logs openmrs-app` on unrelated scheduled tasks too, so this is a
standing, pre-existing logging gap, not something introduced today.

**Applied:** added the missing keys to the live resource file, matching the values
`defaults.properties` already uses:

```
favicon=/images/openmrs-favicon.ico
favicon.png=/images/openmrs-favicon.png
```

**WHERE:** inside the `openmrs-app` container, in the **persistent** `openmrs_data` named
volume (survives restarts) — NOT in this git-less project's own files:
`/usr/local/tomcat/.OpenMRS/.openmrs-lib-cache/reportingcompatibility/themes/green.properties`

Backed up first to `green.properties.bak-20260907-152840` in the same directory (inside the
container/volume — not in `backup files/`, since that convention covers host files and this
lives only in the Docker volume).

**Applied via:** `docker restart openmrs-app` at 15:30:32, back up and responding within
~2 minutes (same order of downtime as the c3p0 fix in §4.1).

**Verified:**

| Check | Result |
| --- | --- |
| All 7 project containers + NPM | `Up`, MySQL/Postgres/medreport-rgs `healthy` |
| `http://10.0.211.249:8080/openmrs/` | 200, renders the normal login page (French, matching `default_locale=fr`) |
| `docker logs openmrs-app` after restart | clean, no new errors |

**NOT fixed — could not be captured this session:** the *original* exception that the
error page was trying to display in the first place. It only reproduced once, in one
browser tab's existing session; after the restart (which invalidates in-memory Tomcat
sessions), the same navigation now succeeds cleanly and the trigger condition could not be
reproduced. Because `MEMORY_APPENDER` was broken, that original exception was never written
to any log — this fix does not recover it retroactively.

**If it happens again:** this fix means the error page will now render fully instead of
crashing, so the real exception **will be visible directly in the browser** — capture that
page immediately (screenshot or "View Source") before navigating away or logging out,
since the trigger looked session-specific and may not survive a refresh.

**Still open:** `MEMORY_APPENDER` should be fixed properly (its Log4j config) so future
errors are captured in logs regardless of whether anyone catches the browser page in time.
Not attempted this session — out of scope until the next occurrence gives something
concrete to chase, per this project's "read-only investigation before any write" rule.

**ROLLBACK:**
```bash
docker exec openmrs-app sh -c 'cp /usr/local/tomcat/.OpenMRS/.openmrs-lib-cache/reportingcompatibility/themes/green.properties.bak-20260907-152840 /usr/local/tomcat/.OpenMRS/.openmrs-lib-cache/reportingcompatibility/themes/green.properties'
```

## 4. Priority 3 — hardening

### 4.1 Connection-pool validation (the recurring 500s) — ⚠️ APPLIED 2026-09-07, effectiveness not yet observed

**The originally planned fix would not have worked — caught before applying it.**

The handoff's draft proposed `hibernate.c3p0.preferredTestQuery`,
`idleConnectionTestPeriod`, `testConnectionOnCheckout`. Before writing those, the actual
`hibernate-c3p0-5.4.21.Final.jar` bundled in this deployment was inspected directly
(bytecode string constants, not documentation). **Hibernate's `C3P0ConnectionProvider` in
this version forwards only six `hibernate.c3p0.*` keys** — `min_size`, `max_size`,
`timeout`, `max_statements`, `acquire_increment`, `idle_test_period`. The three originally
planned keys are not among them and would have been silently ignored: written to the
file, loaded, and never reaching c3p0.

**A second correction:** OpenMRS's bundled `hibernate.default.properties` already sets
`hibernate.c3p0.idle_test_period=3000` (50 min) — some validation was already active,
contrary to the original assumption that none existed. The Aug 30 incident happened
despite this. A plausible contributor, not fully confirmed: `hibernate.c3p0.timeout=100`
(also a default, mapping to c3p0's `maxIdleTime`) lets the pool shrink toward
`min_size` (previously **0**) after just 100 seconds of inactivity — connections can be
evicted before the 50-minute test cycle ever inspects them.

**Applied, using only the six confirmed-working keys:**

```
hibernate.c3p0.min_size=2
```

in `openmrs-runtime.properties` (on the named volume, edited via `docker exec`, backed
up first to `backup files/openmrs-runtime.properties.bak-20260907-114427`), followed by
a restart of `openmrs-app` (~2 min downtime, same as the original incident's recovery).

**Verified:** file content correct after edit; OpenMRS came back up cleanly; imaging
module still `1.2.0` and started; `settings.list` and the OHIF/DICOMweb chain both
healthy post-restart; zero stale-connection errors since restart (expected — a fresh
pool has none to shed).

**NOT verified, and can't be from this session:** whether `min_size=2` actually prevents
the multi-day-idle failure. Minutes after restart, 22 connections were still open at
~58s idle — under the 100s `maxIdleTime` threshold, so no shrinkage has occurred yet to
observe either way. The only real test is the same timescale as the original incident:
**does `settings.list` / any admin page still 500 after this server sits idle for
several days?** If it recurs, the stronger fix (a `c3p0.properties` file or
`-Dc3p0.testConnectionOnCheckout=true` JVM flag, both proposed and declined at this
session's decision point) should be revisited.

**ROLLBACK:** `docker cp "backup files/openmrs-runtime.properties.bak-20260907-114427" openmrs-app:/usr/local/tomcat/.OpenMRS/openmrs-runtime.properties && docker restart openmrs-app`

### 4.3 Credentials publicly exposed on GitHub — ⚠️ ACCEPTED RISK for development, MANDATORY before production (recorded 2026-09-07)

**This is not a to-do. It is a decision, made explicitly by the maintainer on 2026-09-07,
to accept a known risk during development.** Do not act on this section without a fresh,
explicit decision if the deployment target ever changes from "development" to anything
resembling production or real patient data.

**What was found**, investigated because the handoff had assumed credentials were merely
"inline in compose files" — a routine hygiene item. The actual finding is more serious:

- The project's GitHub remote, `github.com/bouzenaali/openmrs-orthanc-integration`, is
  confirmed **public** (`"private": false` via the GitHub API).
- `origin/main`'s current tip (not just old history) tracks a **committed `.env` file**
  and `orthanc-docker-compose.yml` with inline secrets.
- **Both are live, not stale placeholders.** SHA-256 of the committed `.env` matches the
  local, currently-used `.env` exactly. SHA-256 of the committed
  `ORTHANC__REGISTERED_USERS` line matches what is actually running in production right
  now, exactly. This was confirmed without ever printing either secret value.
- Consequently: **anyone on the internet can currently read the real Orthanc admin
  password and the real `MEDREPORT_RGS_TOKEN`.** The Orthanc password grants full
  DICOMweb access — including deletion — through the entire auth-injection chain this
  project built.
- The local repository was also found to be **7 commits behind `origin/main`** — someone
  pushed independently of this session (an `ohif integration + hospitalCA certificate...`
  commit, among others). Do not assume the local working tree and `origin/main` match;
  they did not.

**Explicit decision recorded here:** for this **development environment**, the maintainer
has decided **not** to rotate these credentials, **not** to make the repository private,
and **not** to rewrite or purge the exposed git history. This is accepted as-is for now.

**Documentation was updated to reflect this decision** — see `README.md` → *Security
notes* and `OHIF-Integration-Architecture.md` → *Known limitations*, both dated
2026-09-07.

---

**Before ANY production deployment, all of the following are mandatory — not optional:**

1. **Rotate every credential that was ever committed**, not just the Orthanc password:
   the Orthanc admin password, the MySQL root/app passwords, the PostgreSQL password, and
   `MEDREPORT_RGS_TOKEN`. Treat every value that has ever appeared in this repository's
   history as permanently compromised, even after this rotation — see point 3.
2. **Move every secret out of tracked files and into `.env`**, and confirm `.env` is
   actually listed in `.gitignore` (it currently is not) before the next commit.
3. **Address the git history, not just the current tip.** Rotating values going forward
   does not erase them from history — anyone who already cloned the repo, or who reads
   its commit history on GitHub, retains the old credentials indefinitely. Either rewrite
   history (`git filter-repo` or BFG, then a coordinated force-push — highly disruptive to
   any other clones, needs explicit authorisation, out of scope for a routine session) or
   accept that those specific old values must never be reused anywhere, ever, even as a
   "fixed" default.
4. **Make the repository private**, or verifiably confirm production secrets are fully
   decoupled from it (i.e., production would use different credentials than any that were
   ever public, making the public history's exposure moot rather than remediated).
5. Only after 1–4: re-run the sequenced credential change below, and re-verify §3.2.

**The three-places-must-change-together trap** (still true whenever rotation happens):

| Place | What |
| --- | --- |
| `orthanc-docker-compose.yml` | `ORTHANC__REGISTERED_USERS` |
| `orthanc-cors-proxy.conf` | `proxy_set_header Authorization "Basic <base64 of user:pass>"` |
| `imaging_OrthancConfiguration` table | `orthancPassword`, via **Administration → Configuring the Orthanc server** |

Changing only the first produces a working-looking system where OHIF 401s and OpenMRS
uploads fail silently until someone checks.
